# 4. Security, privacy, and Cloudflare deployment architecture

## Threat model and security controls

Trust boundaries: anonymous browser -> first-party web/API; web/API -> D1/R2/Queue; Worker -> OIDC and email/AI providers; imported/generated pack data -> schema interpreter; participant -> other participants' data; deployer/operator -> Cloudflare account. Threats include forged sessions, cross-instance IDOR, pack prompt injection, rule escalation, AI data exfiltration, small-cohort inference, email enumeration, queue replay, supply-chain compromise and leaked R2 URLs.

- Authentication: Microsoft Entra ID and Google Workspace OIDC Authorization Code + PKCE, verified issuer/audience/signature/expiry/state/nonce, bounded JWK cache, issuer+subject account link; fail closed on provider ambiguity. Require configured corporate tenant/domain allowlists where supported, never trust email domain alone as identity. Magic-link auth is optional, uses work-email allowlist, single-use short TTL hashed token, fixed public response, quotas/cooldowns and a deployer-provided transactional email adapter (Cloudflare Queues does not deliver email). SAML/SCIM remain explicit future adapters with signed assertions/provisioning validation, not placeholders treated as working features.
- Sessions: server-side revocable, hashed rotating opaque session ID; Secure/HttpOnly/SameSite=Lax cookie, strict session expiration; rotate on login and privilege change; Origin check + CSRF double-submit or bound server token on every unsafe action, rate-limit and anomaly log. OIDC/magic callbacks use independent anti-CSRF checks. Configure trusted proxy/host redirects explicitly.
- Authorization: least-privilege RBAC + per-instance participation, explicit grants, server-enforced ABAC (phase, pack capability, privacy/consent) on reads and writes. Query repositories always scope by organization and instance. Admin impersonation is out of scope. Sensitive admin actions require recent authentication and audit.
- Secrets and encryption: AI/OIDC/email credentials and application keys are per-environment Cloudflare Worker secrets, never committed to config or exposed to client bundles. Use envelope encryption/AES-GCM via Web Crypto for optional sensitive D1 payloads, with versioned key IDs, distinct encryption and lookup-HMAC keys, rotation/re-encryption procedure; Cloudflare D1 does not itself imply application-level field encryption. Encrypt private R2 objects when policy requires beyond provider encryption; control key ownership and backups. No sensitive payloads in URLs, queue bodies, logs or analytics.
- Browser and content: strict CSP with nonces/hash policy compatible with Next.js, frame-ancestors deny, HSTS, safe redirects, escaped branded templates, sanitized rich text/HTML if allowed, MIME and size validation on uploads, malware screening policy before serving assets, private download authorization; avoid public R2 buckets and long-lived signed URLs. Privacy policy determines whether recognition messages are visible.
- Supply chain: pinned dependencies/lockfile, dependency and secret scanning, SBOM, signed release artifacts, reviewed migrations/pack manifests, CI permission minimization. Pack manifests do not execute JavaScript. Administrative API endpoints and audit logs are distinct privileges.
- Availability: per-route/actor limits (Cloudflare WAF/Rate Limiting where available plus application counters as appropriate), request size caps, AI token/cost budgets, queue retry ceilings and DLQ, circuit breakers, operational alerts. Do not rely on free-tier limits for capacity planning.

## Privacy architecture

Data inventory: corporate OIDC opaque subject and optional display name/work email for identity and delivery; voluntary preferences/time zone/work metadata for matching; private optional recognition/conversation text; derived profile traits with source and consent; aggregate analytics. Never ask for home address, personal email or phone. Secret Santa supports digital/independent gift delivery; participants arrange physical exchange off-platform if desired, without storing addresses. Remote-friendly missions, asynchronous alternatives, accessible content and no automatic geographic exclusion except an explicitly justified constraint.

Consent registry is part of versioned participant profile: per-purpose grants for profile derivation, AI processing, messaging and insights surveys. Core membership/required access uses a documented lawful basis set by deployment owner; do not imply optional features are mandatory. Respect withdrawal at every read, job and provider call; annotate stored derivatives with consent version and expiry. Deletion workflow traces identity-linked records, purges optional content and R2 objects, removes pending notifications and regenerates aggregates; legally required append-only audit entries retain minimized pseudonymous facts for bounded retention. External AI requests are disabled unless an owner explicitly approves purpose, region/provider policy, DPA/retention terms, and data categories. Encrypt optional private text at application layer. Provide admins with configurable retention, export and deletion with identity verification; do not assert regulatory certification. Log access to sensitive exports and profiles. DPAs, residency, employment-law notice and retention schedules are deployment responsibilities, documented in installation guide.

## Cloudflare resources per environment

| Resource | Purpose / binding |
| --- | --- |
| Web Worker (Next.js adapter) | branded app, SSR/static assets, same-origin API path routing |
| API Worker (Hono) | `/api/v1` via route/service binding, D1/R2 bindings, auth, domain services |
| Jobs Worker | Queue consumer, scheduled outbox dispatcher/cleanup/insights refresh; minimal required bindings |
| D1 database | authoritative application records, migrations and outbox |
| Private R2 bucket | branding assets, scoped exports, draft assets; explicit lifecycle expiry |
| Queue + dead-letter queue | notifications, matching, AI, lifecycle, analytics with bounded retries |
| Worker secrets | encryption/HMAC keys, cookie keys, OIDC/email/AI credentials |
| Optional Workers AI binding | Cloudflare AI adapter only when enabled |
| Cloudflare observability | structured redacted logs, traces and queue/DLQ alerts |

Use dev/staging/prod in separate Cloudflare environments/accounts or distinctly isolated resources; never point preview deployments at production D1. Provision resources and Worker routes declaratively from checked-in templates; each company supplies its own account IDs, tenant/provider config, domains and secrets outside version control. Installation config (validated and revisioned) includes organization name, theme tokens/assets, terminology/locales, enabled pack versions, auth provider settings (non-secret), AI purpose/provider/model selection (non-secret), privacy/retention, email templates and queue controls. Design a sample config schema rather than binding branding or an Azure tenant to source. Deploy order: provision resources -> set secrets -> apply backward-compatible D1 migrations -> deploy consumers/API/web -> configure DNS/identity redirects -> seed first-party pack manifests -> smoke test -> enable traffic. Roll back application using compatible schema; migrations are forward-only with tested recovery from backups/exports and an explicit restore drill. Keep first admin bootstrap via one-time, time-limited, installation-local setup flow; disable after completion.

## Event processing and failure semantics

D1 transactions write state change + audit fact + outbox event together. Queue publication is **not** atomic with D1: a scheduled dispatcher leases unpublished outbox rows, sends reference-only event envelopes to Queue, marks published after acknowledgement, and retries expired leases. Crash after send before marking can duplicate; consumers verify event ID with `job_receipts` and idempotent state transitions. Be careful to record a receipt in the same D1 transaction as domain effects; for external email/AI side effects, persist a delivery attempt keyed by idempotency ID and use provider idempotency if available; otherwise duplicates are possible, explicitly monitor/reconcile rather than claiming exactly-once. Jobs re-check current consent/state before work and cancel stale actions. Dead-letter messages are redacted; privileged replay is audited and requires scope checks. No request waits on bulk matching/AI or sending notifications. Scheduled transitions use UTC schedule, configurable time zone for authoring, catch-up for downtime and optimistic state guards. Bound per-invocation work and paginate D1 processing.

## Operational readiness and verification gates

Before a production deployment: current adapter/Workers runtime compatibility matrix tested (Next.js feature support, Node APIs, image/font behavior and middleware), D1/Queue/R2 binding checks, load test at 1,200 participants and matching candidate limits, migration and restore rehearsal, OIDC/magic-link negative tests, accessibility audit (WCAG 2.2 AA target), privacy export/erasure exercise, multi-time-zone/DST tests, pack conformance, AI egress review and disabled-AI fallback. Define SLOs for API latency, job lag and notification delivery per installation; alert on queue DLQ, outbox age, failed auth spikes, AI budget, migration drift and low storage headroom. Cloudflare plan/limits, provider data processing regions and retention must be checked against the actual installation account; no blanket promise of residency or exactly-once delivery.
