# 3. AI, rules, matching, and insights architecture

## AI control plane

The AI Culture Copilot is an application service, not a privileged autonomous agent. Its orchestration path is: classify request and approved data -> minimize/redact -> select installation-configured provider/model/purpose -> render versioned, bounded prompt -> call provider behind an interface -> validate typed response -> run deterministic rules and pack schema checks -> show provenance, cost and uncertainty to a human -> explicitly approve any publication/action. Every provider may be disabled; deterministic manual workflows still work. No promise of equivalent model behavior across providers.

Provider interface: `generateStructured(purpose, schema, messages, policy, budget, abortSignal)` and optional `embed` (off by default); adapters for OpenAI, Azure OpenAI, Anthropic and Cloudflare Workers AI. Adapters handle credentials from Cloudflare secrets, API version/model mappings, deadlines, retry/backoff with jitter, rate/cost limits, regional endpoint policy and normalized error classes. For unsupported schema-native output, parse and validate strictly; never trust generated JSON. Cloudflare AI models and residency vary by deployment: configuration, not assumptions. Prompt and response must stay within the deployer's configured data-egress policy; providers have no direct D1/R2 access. Record provider/model/prompt version and sanitized usage metadata; default no raw transcript storage. External-provider settings require an explicit privacy review of retention/training/data transfer terms; per-purpose disable switches and local-only mode are available.

Copilot inputs: organizational size bands, remote distribution, departments/geography/time zones in coarse aggregates, objectives, budget and consented participation data only. It returns typed recommendations `{ packId, fitReasons, matchingStrategy, communicationPlan, participationPlan, revealPlan?, metricPlan, risks, assumptions }`. Present meaningful alternatives and allow manual override; do not infer protected characteristics or score individuals from unconsented data. Pack builder outputs a **draft manifest** following the same data-only manifest schema as a human-authored pack: objectives, eligibility, matching, missions, activities, workflow, communications, assistant prompts, analytics and inclusivity alternatives. Dry-run sample scenarios, schema/capability check, prompt-injection scan, privacy/egress check, human admin approval and immutable publication are mandatory. Unsupported mechanics produce a validation error and a proposal for a reviewed new capability, not executable generated code.

For communications/branding/gift suggestions: restrict output to approved organization tone and locales; treat participant and pack text as untrusted data; avoid unsolicited gifts/physical-delivery assumptions; give accessible plain-text equivalents; require human approval before sending. Matching AI may propose or tune **bounded weights** or explain aggregate outcomes, but cannot override deterministic eligibility, consent or fairness constraints. No participant-level profiling from message text by default.

## Declarative rules engine

Rule DSL (typed schema, not a programming language): `{ id, category, priority, when: Predicate, then: Effect }`; predicates are bounded `all`, `any`, `not`, or leaf comparisons of allowlisted fields (`participant.team`, `participant.department`, `participant.timeZone`, `participant.remotePreference`, `participant.tenureBand`, `instance.phase`, `consent.scope`, `priorMatch.count`). Operators: equality, finite-set membership, range for approved numeric/band fields. Effects: `allow`, `deny`, `requireApproval`, `setPrivacyMode`, `setMatchingConstraint`, `setActivityCapability`, `setPool`, `scheduleRelativeAction`. No loops, user-defined expressions, dynamic SQL, provider calls, arbitrary paths or network requests. Validate nesting depth, input size, enum values, required field availability and incompatible effects on publication.

Evaluation order: installation safety policy > consent/privacy controls > template eligibility > experience overrides > per-action guard. Deny wins over allow at the same authority level; lower authority cannot weaken higher-level safety. Matching hard constraints are resolved before weights; rule priority cannot bypass consent. Log rule IDs and decision codes, not participant traits. A dry-run endpoint reports conflicts, unsatisfiable enrollment and scheduled transitions before launch. Timezone overlap uses IANA zones and interval conversion at scheduling time, including DST. Participation modes mandatory/optional/invite-only cannot legally force collection of optional profile data; mandatory is an organization enrollment policy requiring local HR/legal review. Privacy modes anonymous/pseudonymous/reveal-at-end/never-reveal are enforced on every read and notification, not merely the UI.

## Scoring-based matching engine

Strategies implement `eligibleGroups(input, constraints)`, `scoreGroup(group, context)`, and `explain(scoreComponents)` over a versioned immutable input snapshot. Built-in strategies: CrossFunctional (reward different departments, avoid repeat), DiversityOptimized (maximize organizational exposure across non-sensitive metadata, never demographic protected traits), RemoteFirst (remote-compatible formats and overlap), NewHireFriendly (eligible buddy and capacity/tenure), LeadershipMix (role-level eligibility, power-dynamics safeguards). Do not use uniform random assignment or AI as the matcher. First-party pack manifests select a strategy key, bounds, weights and constraints. Custom data-only strategies can combine registered scoring components; new algorithms require reviewed core code.

Pipeline: enumerate opt-in eligible participants -> partition only when justified by legal/geographic/time-zone rules -> filter forbidden pair/group edges (self, opted-out, prohibited repeat, capacity, no consent, impossible schedule) -> normalize features and apply bounded weighted scores -> optimize globally (maximum-weight matching for pairs; bounded deterministic candidate generation and set-packing for small groups, with documented approximate fallback above size thresholds) -> report unmatched and constraint violations -> dry-run fairness and privacy checks -> designer approves -> persist and publish. Stable ID-based tie-breakers make runs reproducible; tie-breakers do not reintroduce randomness. Batch large groups in a Queue consumer; set capacity/time budgets, provide deterministic approximation diagnostics, never silently relax hard constraints. Consider D1 operational limits and chunk candidate generation rather than materializing all $O(n^2)$ edges for 1,200 people. An instance-local prior-match history and consented profile traits influence weights; absence of optional metadata yields neutral scores rather than exclusion.

Fairness report: participation and unmatched counts by sufficiently large organizational cohorts, match quality distribution, repeat exposure, remote/time-zone compatibility and load balance. Suppress small cells and do not infer or display protected groups. Human designer may change weights within policy but cannot bypass hard rules. Odd cardinality: triad if pack permits; else mark unpaired with explicit designer decision and participant-safe communication. Publishing a match run uses transactional single-winner compare-and-swap; retries reuse the same input hash/strategy and job receipt. Participant-facing peer visibility is gated by privacy/reveal rules.

## Insight engine

Metric definitions are versioned, permissioned and computed from participation/activity/match events, not raw conversation content. Examples:

| Metric | Proposed calculation / caveat |
| --- | --- |
| Participation rate | enrolled eligible / invited eligible, counting opt-outs distinctly; denominator must be known |
| Engagement rate | participants completing at least one approved meaningful activity / enrolled participants |
| Connection score | consented post-experience survey composite, reported only as aggregate; show response count/bias |
| Department bridge score | cross-department completed connections / completed connections with known department |
| Organizational reach | distinct departments connected / departments with enrolled participants |
| Remote inclusion score | remote participant completion rate relative to all participant completion, with cohort suppression |
| Experience completion rate | participants completing pack-defined required milestones / enrolled participants |

Definitions include denominators, window, inclusion rules, minimum cohort threshold (default 10, configurable upward), quality flags and version. Suppress complementary totals and repeated/filterable queries that could reconstruct individuals; restrict free-form filters and apply rate limits. Insights recommendations use only pre-approved, sufficiently aggregated metrics: e.g. low Marketing/Technology interaction -> propose Cross-Team Connector, display evidence, sample size and uncertainty. AI does not receive participant names, recognitions, message text or identifiers for this purpose. Snapshots are materialized asynchronously on state changes/schedule; communicate freshness and missing data. No individual performance or employment decision use. Feedback is opt-in and may be deleted according to retention policy.
